# Architecture

The proposed Phase 3 search, PDF page selection, generation history and study progress work is planned in [PHASE_3_PROJECT_MAP_AND_MILESTONES.md](PHASE_3_PROJECT_MAP_AND_MILESTONES.md). Its milestones are pending implementation.

Implemented through M7 and Phase 3 P3-M1 (workshop name search), P3-M2 (PDF page selection), P3-M3 (persistent generation history), P3-M4 (Reuse settings and History path reconciliation), P3-M5 (persistent study progress) and P3-M6 (Phase 3 packaged build, verified end to end with real Gemini and LaTeX on 2026-11-09), plus the LaTeX-body migration (packaged as a Windows one-folder build): workshop shell, shared pipeline, all eight tasks with their output layouts, Efficient (local text conversion) with caching and scan handling, and bounded recovery with actionable errors. Package root: `src/late_night_workshop/` (internal id; the app's display name is Late Night Pal). The proposed full plan is in `components.md` and `PROJECT_MAP_AND_MILESTONES.md`; this file lists only what exists.

Pipeline order (`generation.generate`): validate parameters and paths → LaTeX + destination preflight → prepare inputs (every PDF inspected with pypdf, so encrypted/unreadable PDFs and bad page choices fail here; original, selected-page subset or local text; scan decisions go back to the UI, and Cancel ends here with zero API calls) → resolve task → **one** Gemini request (JSON metadata + one `latex_code` body per document) → validate the bundle contract → check each document (static LaTeX rules, task content) → compile every PDF in a restricted lualatex process in a temp dir and check page counts → publish (all or nothing). The only extra Gemini requests, each announced in the status: one retry after a network error, one bundle repair after a failed contract check, and **at most one targeted repair per failed document** (unsafe or incomplete LaTeX, compile error, too many pages); documents that passed are never regenerated. Publish failures never call Gemini.

**Ownership.** Gemini owns document content and LaTeX layout (the body between `\begin{document}` and `\end{document}`). Python owns document identity (roles, days, `document_id`, title and subtitle placement), expected roles and counts, filenames and paths, the preamble and package allowlist, validation, compilation, page counts and publication.

## LaTeX isolation

Generated LaTeX is treated as untrusted, executable-like input: a prompt injection in a source file could ask Gemini for hostile code. Probed on this PC before the change: with only `-no-shell-escape`, a body could read any file the user can read (`\input{C:/…}` or Lua `io.open`) into the PDF, and could see `GEMINI_API_KEY` (`os.getenv`; `load_dotenv` puts it in the app's environment, which the compiler inherited). Writes outside the job folder and program launches were already refused by MiKTeX. `--safer` is not usable: fontspec fails under it. Layers now:

1. **Static check** (`validation.latex_problems`) before any compile; violations go to that document's one repair.
2. **Separate restricted process** (`rendering.run_sandboxed`). Generated LaTeX is never compiled in the app process. It runs with the job temp folder as cwd, `-no-shell-escape -halt-on-error`, an environment reduced to `ENV_KEEP` + `MIKTEX_*` (no key), and a 180 s timeout per pass. On Windows the process starts suspended inside a job object: `ActiveProcessLimit` 1 (no child programs), 2 GB memory, no clipboard, desktop or global-atom access, killed when the job handle closes.
3. **Read guard** (`templates/guard.lua`) for anything the static check misses.

Verified (`tests/test_latex_pipeline.py` · `Sandbox`): a body that uses Lua `io.open` and `\openin` on a file outside the job folder, and `os.getenv("GEMINI_API_KEY")`, prints neither the file nor the key.

**Known limits (not solved in this scope).** This is not an OS sandbox such as an AppContainer or a separate user account: lualatex still runs as the user. The denylist and guard are best effort against TeX's macro language. A body that defeats both could read files with TeX-like extensions (`.tex`, `.sty`, fonts…) outside the job folder, or fill the temp disk until the timeout. The PDF stays local and is published only after all checks pass. The compiler has no network module, so it sends nothing anywhere.

## Generation and errors

`generation.py` · `generate(request, on_progress, deps)` returns `{status, output_root, paths, warnings, timings: {gemini_s, render_s, publish_s}, documents: [{document_id, page_count, render_s}], generation_id, history_record}` (P3-M3: the id is `request["generation_id"]` or a new uuid; the record is built right after publication from the sources and rendered documents, so temp cleanup can't lose it; a build failure leaves `history_record: None` + `history_error` and the result stays `ok`. `generate` never saves history: the UI worker does, so `--summarize` and stubbed runs write none) or `{status: "error", error: envelope}`. `deps` swaps `check_runtime` / `generate_content` / `render_bundle` / `publish` for stubs. `decide_inputs(decisions) -> {source_id: "process_original"|"cancel"}`: anything other than process_original for every pending source returns `{status: "cancelled"}` before any API call; otherwise preparation reruns with those `original_overrides`. Without a `decide_inputs` callback (the CLI), the job is cancelled. Bounded recovery: `ask_gemini` retries once only after `api_network` (quota, auth and limit errors are not retried). `validated` sends one `REPAIR_PROMPT` request for a failed bundle contract (the problem, the task prompt and the previous JSON, without re-sending sources) and fails with "… (also after one repair attempt)". Then every document goes through `document_problems` and `render_bundle`. Each failed document (static problem, `compile_failed` or `page_limit_exceeded`) gets one `repair_document` request: `DOCUMENT_REPAIR_PROMPT` with the problem (LaTeX error lines or page count), the task prompt and that document's `latex_code` only, schema `tasks.REPAIR_SCHEMA` `{latex_code}`, no sources. The repaired body is rechecked and recompiled once; a second failure ends the job with its code (`invalid_response`, `compile_failed` with the log path, `page_limit_exceeded`) and "(also after one repair attempt)". Publish errors never call Gemini. Rendering happens in a `TemporaryDirectory` that is always removed. `__init__.py` · `AppError` subclasses give `{code, stage, message, source_id, retryable, details}`.

## Organizer, name tags and downloads (Phase 2, P2-M1, P2-M3–P2-M5)

Organize mode runs Delete, Rip, Wrap, Copy, Paste and Super Wrap, and drag and drop (move inside the workshop, copy from Recent downloads) uses the same chain from `Window.handle_drop()` → `plan_drop`: `Window.organize()` → `capture_request` → `plan_action` → (confirm) → `OrganizeWorker` → `execute_plan` → `workshops.reconcile` → `clipboard_after` → refresh and `describe_outcomes`. Only `execute_plan` and the adapters change files; it runs generic folder creation and moves and never knows which action built the plan. Full rules are in `components.md` → Organizer.
